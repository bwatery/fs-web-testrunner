## 一、这一步要做两件事，一件事两个面孔

| | 给谁用 | 形态 |
|---|---|---|
| **界面认证** | **给人看** | 有头/窗口模式，能出截图，能盯着它跑 |
| **无头模式** | **给 AI 快速测** | 无头跑，不打扰人，能反复跑、定时跑 |

**但两者是同一套判定**：都连真库、都读页面渲染出来的值、都跟库做等式/集合对账、
**判「通过」的门槛完全一致**。区别只是"浏览器怎么起"。

> ⚠️ **无头不是降级模式。** 如果一个断言在无头下跑不了，就**如实报「未执行」并说明**，
> 不许降级成"页面打开了没"这种弱断言充数。

## 二、要做出来的东西

### 1. 浏览器层 `fs_runner/browser/`
- 自建 CDP 客户端（**照 `verify/workstation_check.py` 的做法**，它已经自建了、刻意没用旧 `core/browser_driver`）
- `--headless` / `--windowed` **必须可选，默认 `headless`**
  - `windowed` 连的是用户正在看的那个 Chrome（9222）—— 点菜单时用户屏幕上会跟着跳，只适合"我盯着看一次"
  - `headless` 自己起一个新实例，不干扰用户
- 起不来 / 连不上 → **报错退出，不许静默降级**

### 2. 登录（界面认证通道）
- 走**真实登录页**输入账号密码，拿到会话 —— **不要注入 token 假装已登录**
  （方案 §4.5：用户明确要求"后面最好能够在页面上认证"）
- 登录失败要能区分"账号密码错"和"页面根本没起来"

### 3. 新子命令
```
python -I fsrun.py ui-verify [--case L6-005,L9-012,...] [--headless|--windowed] [--screenshot]
```

### 4. 至少 3 条用例做到**真的界面认证**（不是界面冒烟）
「打开页面 → 操作 → **读页面上真实渲染的文字/表格** → 与库比对 → 等式成立才叫通过」

建议先做这 3 条（都是"页面上有一张表/一串数字，库里有对应行"的形状，好对账）：
- **L6-005** 门诊挂号列表：页面底部挂号列表 → 读那几行 → 与 `FIN_OP_REGISTER` 比
- **L9-012** 摆药单分类明细对账：`queryDetail` 渲染出的明细 → 与 `PHA_DISPENSE_APPLY` 比
- **L6-050** 收费员日结与缴款：日结页面的收据张数/金额 → 与库比

**选哪几条、放弃哪几条，都要在回执里说明理由。** 宁少勿假。

### 5. evidence 必须能回答
```
界面读到了什么？（选择器/表头/具体单元格值）
库里是什么？
等式是什么？
用哪种模式跑的？（headless / windowed）
```
台账口径新增 `[界面·无头]` / `[界面·窗口]`，与现有
`[闭环真验证·接口+库对账(未点界面)]` / `[打印交回·人工在界面实测]` 并列，**不得混写**。

### 6. ⚠️ 必须沿用的坑：这个前端 **hash 跳转不重新加载组件**
路由变了但内容区还是旧页。**必须补一次 `Page.navigate` + `Page.reload`**，
否则会**在错的页面上做对的断言** —— 那比不验更糟。`ui_walk` / `workstation_check` 已处理，照抄。
