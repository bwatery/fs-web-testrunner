### 回归的红绿灯怎么读（**这条最要紧**）

`tools/collect.py regression` 会区分两类失败：

- **❌ 红 = 新失败** —— 没人见过的，必须查
- **绿（含已知缺陷 N 条）** —— 失败已被登记在 `reports/verify/known_defects.json`，
  **每次都会把 N 条逐条大声列出来**，不静默

之所以要这个区分：**真缺陷修好之前每次回归都红，会把人训练成忽略红灯** —— 而"让人忽略红灯"
正是这个项目成立的原因（旧工具把 320 条没跑过的用例洗成"通过"）。
**任何一条都不许因为"烦人"而加进 `known_defects.json`，只能因为被修复而移除。**

## 5. 口径与陷阱清单（最重要的一节）

**下面每一条都曾经"看起来像系统缺陷"，追查后确认是工具/口径的问题。**
**重复踩等于把假缺陷交给用户。**

### 5.1 hash 跳转不加载页面组件

**现象**：点菜单后标签页名字对了、路由对了，但内容区还是仪表盘。
**真相**：这个前端**对 hash 变化不重新加载组件**，必须整页重载（等价真人按 F5）。
**已修**：`workstation_check.py` 与 `ui_walk.py` 点击后**一律补一次 `Page.navigate`+`Page.reload`** 再判定。

### 5.2 换权会消耗管理员会话

同一 `/login` 令牌**只能 `exchangeLogin` 一次**，且换权会作废原会话。跨用例连续跑时，
不刷新令牌会把后续用例打成 **401**。`closed_loop.run()` 每条用例前重新 `/login`。

### 5.3 退费确认按科室隔离

用**管理员令牌**查 `/faith/finance/inpatient/apply/refund/confirm/patient/list` 永远是**空**。
必须换**住院护士**身份（role 36 / dept 910131）。

### 5.4 日结报表口径之一：预交金 = 操作人 + 时间区间

`/faith/finance/dayBalance/report/prepay/list` **不是**全量报表：

```
口径 = 当前登录操作人 收取的  +  上次日结结束时间 → 现在
```

把全量 183,500 当应计数会得出"差 18 万"的假结论。**两个条件缺一不可。这只适用于预交金。**

### 5.5 日结报表口径之二：门诊票据 / 挂号 = `dayBalanceId`

`/faith/finance/dayBalance/report/outpatient/list` 与 `.../register/list` 必须传
**beginTime + endTime + dayBalanceId** 三个参数：

```
报表 = 收据表 FIN_OP_INVOICE_RECEIPT 中 DAY_BALANCE_ID = 传入 dayBalanceId 的那些行
       （且该日结必须属于**当前登录操作人**，用别人的日结ID查会返回空）
```

- 只传时间区间不传 `dayBalanceId` → **永远返回 0**（参数校验还会报"结束时间不能为空"）
- 返回体 `totCost` 才是总额，`feeInfoList` 是**费用分项**（西药费/中成药/中草药费/诊查费/检查费/检验费/治疗费）
  - ⚠️ **踩过的坑**：页面上「检查费 427.70」曾被当成报表总额，又硬套 5.4 的"操作员+时间区间"，
    于是编出"库 2059.15 / 页面 427.70 / 差 1631.45"的假差异，白查一轮。427.70 只是**一行**；
    真总额 1802.43，与库完全一致。
- `allReceiptNoList` 是文案串：`共 N 张收据其中无效收据共：M张`
  → N = `COUNT(DISTINCT RECEIPT_NO)`，M = `COUNT(DISTINCT RECEIPT_NO WHERE TRANS_FLAG='2')`
- **挂号日结**（`.../register/list`）同一套口径；区别：`registerInfoList[]` 按「挂号级别 × 交易类型」分组，
  且 `quitReceiptNoList` 里的金额是 **`regCost`（挂号费）不是 `totalCost`（实收）**——
  222 的退号组 `regCost=-36 / totalCost=-32`，票据串加起来是 **-36**。拿 totalCost 比会误判成缺陷。

### 5.6 门诊「待收费用」= `BALANCE_FLAG='0' AND VALID_FLAG='1'`，按处方号分组

`GET /faith/finance/outpatient/apply/order/needCharge/list?registerId=` 返回结构是
**按处方号（`SEE_NO`）分组**的：`data[].opApplyVOList[]` 才是明细行。
**别把 `len(data)` 当成条数**——那是**处方组数**（勾选单位）。
- 已缴 = `balance_flag='1'`；`CANCEL_FLAG='1'` 的行金额是 0，不参与
- 样本：`registerId=300011099`（20 条 / 461.21 元 / 6 个处方）

### 5.7 可退挂号 = `VALID_FLAG='1' AND BALANCE_FLAG='1'`

`/faith/finance/outpatient/register/view/list` 的 rows 才是可退挂号；
**返回体里的 `total` 不等于可退条数**（它是该患者全部有效挂号数），判定只能看 `data` 行数。

### 5.8 门诊收费写入链（详见记忆 `his-outpatient-charge-chain`）

- **「手工单」没有独立接口**：它是 `POST .../balance/save/preBalance` 里的
  `applyPricing.applyList`，落库后 `FIN_OP_APPLY.DATA_SOURCE_WAY='0'`（手工记账）。
  （`/faith/finance/outpatient/apply/pricing` 是手术划价那套，别用错。）手工单项必须带 `execDeptId`。
- **退费必须两步**：`.../apply/refund/apply`（退费申请）**再** `.../balance/cancel/refund`（取消结算）。
  只调第二步会报"没有需要退费的项目!"
- **可退数量** = `FIN_OP_APPLY.NO_BACK_QTY`，接口在 `apply/settled/list` 的 `noBackQty`；
  超退提示 `申请单[X]的退费数量[3.0]超过可退数量[2]!`（可退数量按整数打印，别拿 2.0 去匹配）
- ⚠️ **一旦对该挂号收过费，就永久不能退号**（`register/cancel` 报"该号已经看诊"）。
  所以收费类用例要**复用一个既有就诊当试验台，绝不能每次新建挂号**，
  否则会把测试库塞满"看起来可退、实际退不了"的假挂号。

### 5.9 发票与支付方式

- `.../receipt/payment/list?receiptId=` = `FIN_OP_PAYMENT` 的行
- `.../receipt/payment/change {receipt, receiptPaymentId, paymentId}` 只对
  **未作废且未日结**（`VALID_FLAG='1' AND DAY_BALANCE_FLAG='0'`）的发票可用，否则报「发票已作废」

### 5.10 作废/启动患者（=卡）

- `POST /faith/patient/invalidate|activate {patientId}` 翻转 `BD_PATIENT.VALID_FLAG`
  （`BD_PATIENT_CARD.CARD_STATUS` 不变）
- **`/faith/patient/list` 不过滤作废患者**；"不可用"要看业务动作：
  作废后挂号预结算报「该患者处于无效状态，无法操作」

### 5.11 门诊医嘱（详见 L2-105/L2-107 的 flow 注释）

- `order/save` 的 body：`{registerId, seeNo, validateOrderComplete, opOrderList:[{mainOrder:{...}}], opOrderAdjuvantList:[]}`，
  `mainOrder` 用 **camelCase**
- `seeNo` 必须用**新的看诊序号**（`GET .../order/nextSeeNo?registerId=`），否则报
  「该看诊号已存在收费/退费医嘱，不允许继续使用！」
- `billId`(处方号) **必填且服务端不自动分配**，否则 ORA-01400 无法将 NULL 插入 `BILL_ID`；
  用 `GET .../order/nextCombId?registerId=` 取一个新号
- 用量规则：**`qty = ordDosage × freqCycleCount × freqDays`**
- `order/treatment/qty/recalculateWithSubItem` 的 `subItemOrder` 是**扁平的 OpOrderDTO 数组**
  （不是 `[{mainOrder:{...}}]`）；附材**不会自动推导**，给空就返回空
- 删除：`POST .../order/delete/idList {registerId, deleteOrderIdList}` → 医嘱与它生成的费用申请**一起被清掉**

### 5.12 住院药房摆药（详见记忆 `his-pharmacy-dispense`）

- `queryDetail` 的 body 是**对象数组**，每项必须齐 `dispenseBillId` + `storageDeptId` + `terminalId` + `dispenseState`
- `dispenseState` 只认 `SENT/PRINTED/DISPENSED/OUTPUTTED` —— ⚠️ **已发药是 `OUTPUTTED`，三个 T**
- 返回的是该单下 `VALID_FLAG='1'` 且 `APPLY_STATE` == 状态码的明细
- **退药执行**：`.../inDispense/dispense`（配药确认）→ `.../output`（发药确认），
  body 都是 `{dispenseBillIdList, operDeptId, operId, storageDeptId}`；回补库存写 `PHA_IOS_RECORD`，
  药品总库存在 `PHA_STOCK_INFO`
- ⚠️ **执行退药后明细的 `OUTPUT_TIME`/`DISPENSE_TIME` 仍为空**，只有单头写 `OUTPUT_OPER_TIME`。
  别拿明细 `OUTPUT_TIME` 当"已发药"判据（会假报失败），要看 `APPLY_STATE`
- ⚠️ `queryReturnTree` 会返回**空 treeList 但 nodeStats 有数**（detailCount=8 而库里退药明细只有 2 条），
  语义自相矛盾，**别据此写断言**

### 5.13 造数自身的坑：身份证号会撞车

`_gen_valid_id_card()` 的顺序码**只有 3 位（1000 个组合）**，用固定种子必然跨轮次撞车，
系统报「该证件类型+证件号已被其他患者使用」→ 建档失败。
**已修**：`_create_test_patient()` 用随机种子 + 撞车重试。

### 5.14 别把「字典漂移」当缺陷

- 挂号级别→诊查费项目字典**会随时间改**（级别 2 在 2026-10-06 被改过），
  改之前挂的号收据金额对不上当期字典是**正常的**
- 该字典查询会**过滤** `COM_BD_ITEM.VALID_FLAG='0'` 的停用项目（级别 3/5 返回 `[]` 是对的）

### 5.15 探针入参会造成假失败

`smoke_api.bucket_response()` 的判定纪律（务必保持）：
- **5xx / 传输失败一律算缺陷**，不因探针带参而降级
- **4xx 级业务拒绝**：探针带了参数就一律降级为 `CANNOT_VERIFY`，
  只有"没带任何入参仍被拒"才算缺陷
- HTTP 200 + 裸数组/无信封对象 = 成功（本项目确实有这类接口）

### 5.16 门诊号序**按午次各自从 1 编号**

**现象**：断言"同医生同天有效挂号号序不重复"**偶发红灯**。
**真相**：号序按 `FIN_OP_REGISTER.SEE_NOON_ID`（1上午/2下午/3晚班…）**各自从 1 开始**，
所以"下午 3 号"和"晚上 3 号"并存是正常的；全天唯一的是 `DAILY_SERIAL_ID`。
实测撞车：`300011139`(午次2,号序'3',流水1423) vs `300011880`(午次3,号序'3',流水1740)。
**已修**：断言补上 `see_noon_id` 维度（注意 `:2` 重复出现会被当成两个位置绑定，要用命名绑定）。

### 5.17 发药明细的 `ORDER_ID` **分两张医嘱表**

**现象**：一度以为"73 条摆药明细里 57 条挂不上医嘱"。
**真相**：`PHA_DISPENSE_APPLY.ORDER_ID` 按**有无床号**分指两表 ——
有床号(住院)→`MED_IP_ORDER`；无床号(门诊)→`MED_OP_ORDER`。两张都 LEFT JOIN 后 **零悬挂**。
（`MED_IP_ORDER` 的 ORDER_ID 只从 4363 起，更早的在门诊表里 —— 只看一张表必误报。）

### 5.18 发药数量**不等于**医嘱数量

`APPLY_QTY` 是**最小单位**、医嘱 `QTY` 是**包装单位**（换算率=同单位取 1、跨单位取 `PACKAGE_QTY`）；
且允许**部分发放**、允许**全退（净 0）**。所以 `APPLY_QTY == QTY` 这个等式**整体不成立**。
真正站得住的不变量只有一条：**不得超发**（按 ORDER_ID 汇总净量，换算回医嘱单位 ≤ 医嘱量）。

### 5.19 跨系统的**床号/科室不能断言相等**

12 名跨系统患者里 6 名对不上，**全部可解释**：转床、转科、以及
**「临床科室 ≠ 护理单元」**（字典 `SYS_DEPT`：`骨一科`=910098 类型 `I`；`骨一科病区`=910134 类型 `N`，
是两条不同职能的记录）。**注意 `COM_BD_DEPT` 不存在**，科室字典主表是 `SYS_DEPT`。

### 5.20 全库「零悬挂」在本测试库**不可断言**

`FIN_IP_REGISTER` 只有 **46 行**，而 `EMR_RECORD` 有 **519 条**（其中 195 条 `PATIENT_TYPE='O'` 门诊，
本就不在住院登记里）。这是**数据集不完整**，不是"跨系统关联断裂"。只能对"四方确实都有数据"的 12 名患者核对。

### 5.21 药品管制的**权威字典在 `SYS_DICT_DATA`**

`SYS_DICT_DATA` 的 `DICT_TYPE='PHA_DRUG_QUALITY'`（15 条）定义：
`S`=麻醉药品 · `P`=一类精神 · `P1`=二类精神 · `O1`=毒性 · `EF`=放射性 · `5`=抗菌 · `EG`=高警示 · `O`=普药 …
**只在 `user_tables` 里按 `%QUALITY%` 搜会得出"没有字典表"的错误结论**（我犯过）。
药品主数据用 `COM_BD_DRUG.DRUG_QUALITY`。

### 5.22 `CHAR` 定长补空格会造成写入超长

`EMR_RECORD_MASTER.PATIENT_TYPE` 是 `CHAR(2)`，实际存 `'I '`（尾空格，DUMP `Typ=96 Len=2: 73,32`）；
而 `EMR_RECORD_MASTER_LOG.PATIENT_TYPE` 是 `CHAR(1)`（历史 102 条全是 `Len=1`）。
后端写日志未 trim → `ORA-12899` → **封存接口对任何病历都失败**。
**这是一次真缺陷，不是口径问题** —— 判断依据：客户端传什么都一样（4 种调用错误完全相同）。

### 5.23 不要**自推公式去凑等式**

曾写出 `先行自付 == 总额 - 起付线`（45.3-42.92=2.38），数值巧合对上了 ——
但"先行自付"和"起付线"在医保里是**两个不同概念**，换个患者就会假失败。
**规则**：断言只能用**库里真实存在的列**，或**分项之和等于总额**这类不依赖假设的真不变量；
找不到就删掉这条，不许倒推。

### 5.24 变异自检的"没变红"**不等于**断言无效

原版 `mutation_selfcheck.py` **只扰动数值列**，对字符串/标志位/时间戳类断言**天然测不到**。
扩展版 `mutation_selfcheck_ext.py` 补上后：62 条里 **52 条变红**。
反过来也要小心 —— **变红里有假阳性**（字符串加后缀可能让按名字查找的流程查空）。
**"仍绿"是更可靠的信号，但读它时必须先看这条用例的断言是不是"行为/结构类"**（那类本来就不该反应）。

### 5.25 防空跑判断依赖"算出来的值"会被污染

L9-013 的防空跑读的是 `COUNT(*) AS n_disp`；变异把它 `+1` 后，判断以为有数据了，
**从「未执行」静默翻成「通过」**。教训：防空跑判断必须把它**当时观测到的值写进 evidence**，
让任何一次"通过"都能事后审计（"它当时看到几条数据？"）。

### 5.26 接口返回「全量 + 标志位」时，**断言两边必须同范围**

**现象**：L6-005 底部挂号列表**突然失败**：`接口 5 ≠ 库 4；接口多出 [300011137]`。
**真相**：`POST /faith/finance/outpatient/register/list {patientId}` **返回该患者全部挂号、
且忽略 `validFlag` 入参**（实测传 `True`/`False`/不传，返回条数完全相同），
每行自带 `validFlag` 字段，**由前端自己筛**。
我原来的断言比的是 **「接口全量」vs「库里 valid_flag='1'」—— 两个范围不一样**，
只因**当时碰巧没有退号**才一直"通过"；今天有一条被测挂号退了号（`VALID_FLAG='0'`），口径错立刻暴露。
**已修**：全量对全量、有效子集对有效子集，比原来更强。
**教训**：`接口 == 库` 这句话本身不完整 —— 必须写清**两边各自的范围**。

### 5.27 采样要避开「空集比空集」

修 L6-005 时顺手发现的：原来按"挂号数最多"采样，抽到一个 **41 条挂号但有效 0 条**的患者，
于是"有效子集一致"那条断言变成 **空集 == 空集**，恒真。
**规则**：采样时要挑**能压住断言口径**的样本 —— 本例应优先选"既有有效、又有退号"的患者。

## 6. 怎么加一条用例

### 单干：写在 `verify/closed_loop.py`

```python
def flow_L6_xxx(ctx: Ctx) -> LoopResult:
    res = LoopResult(case_id="L6-xxx", title="...")
    # 1. 从 Oracle 取样本（只读优先；要造数就用 _create_test_patient / 复用既有就诊）
    # 2. 调接口（ctx.get / ctx.post）
    # 3. 回读（接口 + Oracle 双向）
    # 4. 断言（用等式，不用"存在即通过"；断言必须**能失败**）
    # 5. 收尾清理（写入类必须清理，恢复原状）
    res.status = "通过" / "失败" / "未执行"
    res.note = "人话说明"
    res.evidence = {...}   # 可复现的证据
    return res
```

写进文件末尾的 `_FLOWS = {..., "L6-xxx": flow_L6_xxx}`。

### 并行（多人/多 AI）：写在 `verify/flows/<模块>.py`

```python
# verify/flows/l5_emr.py
from ..closed_loop import Ctx, LoopResult, _oracle_conn

def flow_L5_001(ctx): ...
def flow_L5_002(ctx): ...

FLOWS = {"L5-001": flow_L5_001, "L5-002": flow_L5_002}
```

`closed_loop.py` 会自动 `collect()` 并进去，**不用改公共文件**，多人不会冲突。
详见 `verify/flows/__init__.py` 的约定。
