# 〇、要解决的问题（先把病灶说清）

现状**三层都通不了**：

| 层 | 现在长什么样 | 断在哪 |
|---|---|---|
| 规则 YAML | `statement` 是自然语言 | 机器读不到"它对应哪段代码" |
| 用例 | `flow_X.requires_rules = ['CONV_A','CONV_B']` | **用例级、一整串**，跟具体哪个断言无关 |
| 断言 | `bad.append(f"医嘱数量 {len(api)} 条 ≠ 库 {len(ora)} 条")` | **裸断言**：无规则 ID、无运算符、无结构化两边 |
| 结果 | `LoopResult(status, note, evidence)` | **一个规则字段都没有** |

**后果**：改了规则不知道要改哪段代码；断言失败了不知道违反了哪条规则；
规则库写了没人用也没人知道。今天的 `L6-005→L6-015` 重复踩坑，就是这个断层的产物。

# A · 规则库接入执行链路（三个 hook）

| hook | 作用 | 验收 |
|---|---|---|
| **A1 入口强制** | `regression` / `run` / `ui-verify` 启动时先跑规则校验（schema + 双向一致性 + docstring 检查），不一致**直接中止并返回非零** | 故意改错一条 YAML 的 `affected_cases` → `regression` **拒绝启动**并指名道姓 |
| **A2 证据注入** | 每条结果写入 `evidence["遵循规则"]`（**由断言聚合，不手工维护**） | 随便挑一条结果 JSON，能看到它受哪几条规则约束 |
| **A3 变更点名** | `rules --changed`：比对规则内容 hash，列出"规则变过 → 受影响用例（请重验）" | 改一条规则的口径 → 该命令列出依赖它的全部用例 |

## A 的红线（重申）

hook **只做三件事：拦 / 记 / 点名**。
**不许**因为"规则说应该相等"就去改断言、改数据、改状态 —— 那就滑回旧引擎"自愈"那条老路。

# B · 规则 ↔ 断言 在代码层绑定（第 9 步主体）

## B1 · `fs_runner/rules/ids.py` —— 规则 ID 变成代码常量

```python
# 自动生成，勿手改（由 fsrun.py rules --gen-ids 生成）
RULE_PHA_DISPENSE_NOT_OVER_SUPPLY = "RULE_PHA_DISPENSE_NOT_OVER_SUPPLY"
CONV_DISPENSE_QTY_CONVERSION       = "CONV_DISPENSE_QTY_CONVERSION"
```

- 新增命令 `fsrun.py rules --gen-ids`
- **双向一致性校验**：`ids.py` ↔ YAML 必须完全对齐，多了/少了都报错
- flow 里一律 `from fs_runner.rules.ids import ...`，**不写字面量**

> **为什么**：现在写字符串字面量，**拼错一个字母不会报错**，只会静默变成"这条规则没人用"。

## B2 · 断言原语 `res.assert_rule(...)`

建议放在 `fs_runner/core/assertions.py`（放 `result.py` 也行，你定，但要说理由）。

```python
res.assert_rule(
    RULE_PHA_DISPENSE_NOT_OVER_SUPPLY,
    lhs=net_qty, op="<=", rhs=abs(order_qty),
    sides={"库:发药总量": net_qty, "库:医嘱总量": order_qty},
    desc="发药总量不得超过医嘱总量（含包装换算）",
)
```

**行为要求**：
1. **校验 `rule_id` 在注册表里存在** —— 不存在**立即抛异常**，不许静默通过
2. 记录**结构化**断言：`rule / ok / 等式(人话) / 两边 / statement(从 YAML 取)`
3. **`两边` 必须结构化存**（dict），**不许拼成一个字符串**
4. 失败时把这条断言并入结果的 `断言` 数组
5. 通过时**也要记**（否则"哪些断言真的跑了"看不出来）

**关系算子至少要支持这些**（现有断言里都有，别只做 `==`）：
`==` `!=` `<` `<=` `>` `>=`（浮点带容差）· `in` · 集合相等 · 双向子集 · 逐行字段一致

## B3 · 结果结构扩充

```json
{
  "case_id": "L9-013",
  "status": "阻塞",
  "断言": [
    {"rule": "RULE_PHA_DISPENSE_NOT_OVER_SUPPLY", "ok": true,
     "等式": "发药总量 1.0 <= 医嘱总量 1.0",
     "两边": {"库:发药总量": 1.0, "库:医嘱总量": 1.0},
     "statement": "发药总量不得超过医嘱总量"}
  ],
  "遵循规则": ["RULE_...", "CONV_..."],
  "未归规则断言数": 2
}
```

**关键改动**：`遵循规则` **从「手工在函数属性里写一串」改成「从断言聚合」**。

> 手工那串**一定会漂** —— 这正是现在 `flow_X.requires_rules` 的问题。
> 函数属性可以保留作**声明**，但必须与聚合结果**双向一致**，不一致就报错。

## B4 · 三条硬校验（接进 `rules --check` 和 A1 入口强制）

| # | 校验 | 不通过时 |
|---|---|---|
| 1 | 断言引用的规则 ID **必须存在**于 YAML | 报错，指出**文件 + 行号** |
| 2 | YAML 里的规则**必须至少被一处断言引用** | 报警"写了没人用" |
| 3 | **裸断言必须计数并暴露** —— 结果里必须有 `未归规则断言数` | 计入结果 JSON |

**第 3 条最关键。** 禁止裸断言不现实（有些断言就是一次性的），
但**必须让它可见、可计数** —— 这才让"临时推导的口径"藏不住。

## B6 · 验收（我逐项独立复核）

1. `fsrun.py rules --check` 报出：规则总数 / 被引用数 / **未被引用数** / **未归规则断言数（按用例列出）**
2. 故意在一个 flow 里写一个**不存在的规则 ID** → 校验**报错并指出文件 + 行号**
3. 故意删掉某条规则的所有引用 → 报"写了没人用"
4. `L9-013`（阶段 2 转换后）的结果 JSON 里能看到 `断言` 数组，每条带 `rule / 等式 / 两边 / statement`
5. **反向点名可用**：给一个规则 ID → 列出**引用它的断言**（用例 + 断言描述 + **文件行号**），不只是用例
6. **回归 66 条状态分布**：
   - **阶段 1 必须完全不变**（没改断言）
   - **阶段 2 只允许这两处变**：`L6-015` 失败→通过、`L9-013` 通过→阻塞
   - 其余任何变化 → **停下来报告**，那是改造引入了污染

## B7 · 红线

- **规则库不许改判定** —— 只做 拦 / 记 / 点名
- `assert_rule` **不许**吞掉失败、不许"规则说应该相等所以我就判相等"
- 阶段 1 若导致任何用例状态变化 → **停下来报告**，不许解释成"正常波动"
