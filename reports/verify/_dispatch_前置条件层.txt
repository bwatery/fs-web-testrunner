# 一、最要紧的一条：**补齐 ≠ 自愈**（红线中的红线）

旧引擎的 `self_healing` 之所以有害，是把两件性质相反的事捆在一起：

| | 例子 | 性质 |
|---|---|---|
| **A. 补齐前置** | 开跑前发现没患者 → 用接口建一个 | **正当，该做** |
| **B. 失败后绕过去** | 跑到一半失败了 → 点掉弹层/替它填上 → 仍判 PASSED | **有害，禁止** |

**本轮只做 A。** 任何形式的 B（吞异常、失败后补救后继续判通过、断言放宽）**一律禁止**。

**判据**：`ensure()` 只在**用例开始执行之前**被调用；**执行中**出现的任何失败都必须如实计入结果。

# 二、要建的三样东西

## 1. 标准前置条件词汇表（避免每条用例自造词）

在 `preconditions.py` 里定义一组**可机器判定的**前置条件，每个都给出**检查 SQL/接口**：

```
在院登记 · 有挂号 · 有收费记录 · 有体温记录 · 有护理记录 · 有医嘱
有病史文书 · 有病程记录 · 有检验结果 · 有摆药明细 · 有发药记录
有退药单 · 有电子发票 · 有医保登记 · 有过敏记录 · 在院床位分配 …
```

**先按实际用到的补齐**（从 66 条用例现在各自写的采样 SQL 反推出来），**别凭空造词**。

## 2. 每条用例显式声明 `requires`

- **66 条全部声明**，哪怕为空也要写 `requires = []`（显式 = 可审计）
- 放在 flow 函数上（与现有 `requires_rules` 同位置），例如：
  ```python
  flow_L5_001.requires = ["在院登记", "有体温记录"]
  ```
- 声明后**必须与实际用的采样口径一致** —— 不一致要报错（否则又是一份会漂移的手写清单）

## 3. `ensure()` 真的干活

```
跑用例前：
  ① 按 requires 逐项检查（用词汇表里的检查口径）
  ② 缺的项 → 尝试用「被测系统自己的接口」补齐（不是直接写库）
  ③ 补完 → 回读确认（这一步本身就是断言）
  ④ 补不上 → 返回失败，用例判「阻塞」或「未执行」，写明缺哪项
```

**补齐必须走已有的造数护栏**（`fs_runner/core/audit.py`）：
- 审计、报数、50 条熔断、`cleanup-testdata` 可回滚 —— **一个都不能绕过**
- 补齐造的数据**要带 runId 标记**，便于精确回滚

# 三、跑批结束必须报这张表（这是给决策者的）

```
前置条件统计（本次跑批）
  用已有数据跑通       N 条
  靠自建数据才跑起来    M 条   ← 比例高 = 本环境不具备测试条件
  因前置不足未跑        K 条（逐条写明缺什么）
```

**三个数字都要进结果 JSON**，并且**控制台顶部也显示**。

> 方案原文：**"比例高 = 本环境不具备测试条件 —— 这个结论必须给到决策者，不许被抹平。"**
> 这张表就是那句话的落地。
