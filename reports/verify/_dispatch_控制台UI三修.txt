# 一、`percent` 算错（实测跑到 **400%**）

## 现场
请求 1 条用例（`UI-L6-039-P1`），状态却报：
```json
{"running":false,"total_cases":1,"current_index":4,"percent":400,...}
```

## 根因
`fs_runner/ui/runner_bridge.py:50`
```python
percent = int((self.current_index / self.total_cases) * 100)
```
`current_index` 会被**界面巡检的 4 条子结果**逐个推到 4；而 `total_cases` 是**你勾选的用例数**（1）。
两条口径不同 —— 子结果数是 4、勾选数是 1 → 400%。

## 改法
- **分母要与分子同口径**：若按子结果推进，分母就用**本次实际产出的结果总数**；
  若按勾选用例推进，`current_index` 就不能被子结果推进。
- **无论如何夹到 `min(percent, 100)`** —— 进度条跑到 400% 本身就是 bug 的信号。

## 验收
- 单跑 1 条界面巡检 → `percent` 最终 **= 100**，中途**单调递增、不超 100**
- 单跑 1 条闭环用例 → 同样 100

# 二、独立可见浏览器**跑完不回收**（→ 孤儿进程堆积）

## 现场
用 `show_browser: true` 跑完一次界面巡检后，检查：
```
remote-debugging-port=9333 的 chrome.exe 仍有 8 个进程存活
```
跑一次留一堆，**反复跑会把机器堆死**。

## 根因
`fs_runner/ui/runner_bridge.py:262-288` 的 `finally` + `taskkill` 是**「停止」按钮**的路径。
**正常跑完**的路径没有收尾 → `--standalone` 起的那个独立 Chrome 没人关。

## 改法
- **正常结束路径也必须收掉本次起的 standalone 浏览器**（成功、失败、异常三种出口都要）
- 建议：由**子进程自己在 `finally` 里关**（谁起的谁关），父进程再加一道兜底；
  并按 **实例/端口**记录，**只关自己起的那个**，绝不许误杀用户自己的 9222。
- 收尾后**校验**：该端口上不应再有残留进程

## 验收（我做实跑）
- `show_browser: true` 跑一次 → 跑完 `remote-debugging-port=<临时端口>` 的 chrome 进程数 **归 0**
- **连跑 3 次** → 不累积（每次跑完都归 0）
- **用户自己的 9222 全程不受影响**（跑前跑后都在）

# 三、`UI-L6-039-LIST` 是**假失败**（两边范围不一致）

## 现场（同一台机器，两次运行结果不同）
```
18:04  界面树 19 个床位 ↔ 库 19 个     -> 通过
20:03  界面树  9 个床位 ↔ 库 19 个     -> 失败   (读到的全是 401-* 一个病区)
```

## 根因
`fs_runner/browser/runner.py:253`
```javascript
document.querySelectorAll('.el-tree-node__content')   // 直接读，不先展开
```
**它读到的是「当前展开到哪层就哪层」**，而库里是**全量**。拿"展开的部分"比"全量" —— **这个断言天生 flaky**。

## 改法（二选一，我倾向前者）
1. **读之前先「全部展开」**：把树里所有收起节点的展开图标点一遍，等渲染稳定后再读，
   再与库比对**全集相等**；并**断言展开动作确实生效**（否则又会静默退化成读部分）
2. **改成子集断言**：`界面读到的床位集合 ⊆ 库中登记的床位集合`，
   **并在 evidence 里写明"本次读到 N 个 / 库中 M 个，未展开的部分不计入"** —— 诚实但弱

> ⚠️ 无论选哪种，**都不许**为了让它变绿而放宽成"只要有交集就算对"。

## 验收
- **连跑 3 次**，每次结论**一致**（不许时绿时红）
- evidence 里能看到 **界面读到的数量 / 库中的数量 / 用的是全集相等还是子集**
