# 一、问题（主力自己拆出来的）

现在同一条业务被拆成两套、互不相干：

```
66 条闭环用例（closed_loop.py）  = 接口 + 库对账            ← 完全不碰界面
UI-* 那 12 项（browser/runner.py）= 开页面读渲染值与库对账   ← 另立的一套
```

后果：
- 跑 `L6-043` 这条用例，**只验了接口，没验界面**
- 想验界面得去另一个页面点另一套东西
- `--windowed` 对闭环用例**直接无效**（`runner_bridge` 里 `show_browser` 只在 `is_ui_verify` 分支用）
- **用户在同一个地方踩了两次**（"窗口模式下点了不弹页面"）

# 二、目标结构

**每条用例 = 业务腿 + 界面腿**（界面腿可选，但**必须显式声明"有没有"**）：

```python
flow_L6_043.requires = [...]                 # 已有（前置条件）
flow_L6_043.requires_rules = [...]           # 已有（规则口径）
flow_L6_043.ui_verify = ui_verify_L6_043     # 新增：界面腿（没有就显式 None）
```

运行时：
```
python -I fsrun.py run --cases L6-043                 # 只跑业务腿（默认，快）
python -I fsrun.py run --cases L6-043 --windowed      # 业务腿 + 界面腿，浏览器可见
python -I fsrun.py run --cases L6-043 --ui            # 业务腿 + 界面腿，无头
```

**关键点**：
1. `--windowed` / `--ui` 对**所有**用例都有效 —— **能跑界面腿的就跑，跑不了就如实说明**
2. **不许静默忽略**：某条用例没有界面腿时，结果里要能看到 `界面腿: 无（未实现）`，
   而不是让用户以为"勾了没反应"
3. **界面腿失败 = 这条用例失败**（一个业务点，两条腿都要过）

# 三、第一阶段（本轮）：**先合并已有的 12 条，不新建**

现在有 12 条用例**既有闭环腿、又有界面腿**（`L6-039` `L6-043` `L6-045` `L4-048` `L5-001` `L5-002` `L5-005` `L5-008` `L5-011` `L5-019` `L5-036` …）。

**把它们合并**：跑这条用例时，业务腿 + 界面腿一起跑，**一份结果**。

### 具体做法（建议，可调整）
- 在 flow 上挂 `ui_verify`（指向现有界面断言的函数/ID）
- `run` 支持 `--ui` / `--windowed`
- 结果 evidence 里**两段并列**：
  ```
  业务腿: 接口值 ↔ 库值 + 等式
  界面腿: 页面渲染值 ↔ 库值 + 等式（含选择器、运行模式）
  ```
- 台账备注也并成一条：`[闭环真验证·接口+库对账] …  [界面·无头] …`

### 验收
1. `python -I fsrun.py run --cases L6-043 --windowed` → **浏览器弹窗可见**，并跑完两条腿
2. **同一份结果**里既有业务腿又有界面腿的证据
3. 没有界面腿的用例：勾了 `--windowed` → 结果里**明写** `界面腿: 无（未实现）`，**不许静默忽略**
4. **66 条常规分布不变**：`通过58 失败1 阻塞1 跳过3 未执行3`
5. `ui-verify` **子命令仍然可用**（别把现有入口拆坏），但它和 `run --ui` 应当**共用同一份界面断言实现**，
   不许成为第二套并行的东西（这正是要消灭的病）
