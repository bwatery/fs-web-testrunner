# 第三部分 · 修一个注入时引入的 bug（`__doc__` 全丢）

**实测**：`flows/` 里 38 个 flow + `closed_loop.py` 里 28 个 flow = **66/66 的 `__doc__` 全是 `None`**。

**原因**：你把 `requires_rules = [...]` 写在了函数体**第一行**：

```python
def flow_L9_013(ctx: Ctx) -> LoopResult:
    requires_rules = ['CONV_...', ...]     # ← 第一行
    """出院带药发药 …"""                     # ← 这行就不再是 docstring 了
```

而且**函数体里这行根本不起作用** —— 它只是个局部变量，读完就扔。
真正生效的是模块末尾的 `flow_L9_013.requires_rules = [...]`。

**要求**：
1. 删掉那 66 行函数体内的赋值（保留模块末尾的函数属性赋值）
2. 恢复 docstring（它必须在函数体第一行）
3. **加自检**：`python -I fsrun.py rules --check` 顺带报「N 条 flow 缺文档串」，
   当前必须报 **0**；有 flow 丢了 docstring 就报警

# 第四部分 · 让规则库真正"接入执行链路"（**等主力确认后再做**）

**现状（主力查证）**：规则包在整个仓库里**只有一处**被 import ——
`fs_runner/cli.py:547`（`rules` 子命令）。真正跑 66 条用例的 `closed_loop.py` **一行都没引用它**。

也就是说：**规则库不参与任何断言、不参与任何门禁、不进任何 evidence** ——
只在你主动去查它的时候才存在。**它现在拦不住任何人再次犯错。**

> 活证：`L6-005` 的口径早就写进交接文档和规则库了，但没有任何机制在写新用例时拿它来扫，
> 所以 `L6-015` **又踩了同一个坑**。

**要补三个 hook**（**都不改断言** —— 规则库不该改判定，那就滑回"自愈"那条路了）：

| hook | 作用 | 验收 |
|---|---|---|
| **A. 入口强制** | `regression` / `run` / `ui-verify` 启动时先跑规则校验（schema + 双向一致性 + docstring 检查），不一致**直接中止跑批并返回非零** | 故意把某条 YAML 的 `affected_cases` 改错 → `regression` **拒绝启动**并指名道姓 |
| **B. 证据注入** | 每条结果写入 `evidence["遵循规则"] = [规则ID...]`；规则内容算一个短 hash 一并写入 | 随便挑一条结果的 JSON，能看到它受哪几条规则约束 |
| **C. 变更点名** | `rules --changed`：比对规则内容的 hash，列出"规则变过 → 受影响的用例（请重验）" | 改一条规则的口径 → 该命令**列出依赖它的全部用例** |

**红线**：hook **不许**因为"规则说应该相等"就去改断言、改数据、改状态。
它只能做**拦、记、点名**三件事。
