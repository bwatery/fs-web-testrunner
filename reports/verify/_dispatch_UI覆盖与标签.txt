# 一、给每条用例打「验证方式」标签（用户明确要求，先做）

用例列表每行**加一个标签**，让用户一眼看出这条是怎么验的：

| 标签 | 含义 | 判定依据 |
|---|---|---|
| **`接口`** | 只有接口 + 库对账，**未点界面** | 在 `closed_loop_latest.json` 里，但不在界面巡检结果里 |
| **`接口+界面`** | 除接口对账外，**还有界面断言** | 同时出现在 `ui_verify_latest.json`（按用例ID前缀匹配，如 `UI-L6-039-*` → `L6-039`） |
| **`仅界面`** | 只有界面断言（极少） | 只在界面巡检里 |

要求：
- 标签**醒目**（颜色区分），不要藏在 tooltip 里
- 顶部加一句统计：`已覆盖界面断言的用例：N / 66`
- **不许把"接口"标成别的委婉说法** —— 用户要的就是一眼看穿

# 二、界面巡检支持**单条执行**（用户明确要求）

现在只有「立即执行界面巡检」——一把跑全部，用户说"麻烦"。

要求：
- 界面巡检页**列出每一条巡检项**（`UI-L6-039-P1` / `-P2` / `-LIST` / `UI-INDEX` …）
- 每行一个 **「▶ 单独执行」**，**只跑这一条**
- 保留「全部执行」
- `runner_bridge` / `cli.py` 要支持 **`ui-verify --case <单个巡检项>`**

**验收**：点单条 → 只跑那条 → 更新只反映那条；跑完其余条目的上次结果不被清空。

# 三、把 UI 断言铺开（**本轮的主体，分批做、每批报数**）

## 目标
让 66 条用例里**尽量多**的条目真正走一次界面断言（打开页面 → 读渲染值 → 与库比对）。

## 现实约束（先认清，别硬凑）
- **角色权限**：`admin` 只有住院医生 / 住院护士相关角色；门诊收费、药房发药等页面**进不去**
  （上一轮实测：L6-005 / L9-012 / L6-050 因角色不足被放弃）
- 已证明**可行**的路子：用 CDP 触发「切换科室/角色」对话框换成住院护士 → 能进住院相关页面

## 做法
1. **先做清单**：把 66 条按「页面 + 所需角色」分类，产出 `reports/verify/ui_coverage_plan.md`：
   - **可做**：当前角色能访问的页面
   - **需切角色**：切换后能访问
   - **做不了**：本环境无该角色/无该页面 —— **如实列出，说明原因**
2. **第一批**：挑 **6~8 条**做成真界面断言（优先住院费用 / 在院患者 / 病历这类已验证可行的）
3. 每条必须满足：**页面真实渲染值 ↔ 库值**的等式，evidence 写明
   `界面元素选择器 · 界面读出值 · 数据库真实值 · 验证等式 · 运行模式`
4. **不许**降级成"页面打开了没" —— 那不算界面断言

## 验收（我用 CDP 逐条实跑）
- 第一批 ≥6 条：`--headless` 与 `--windowed` **结论一致**
- **变异自检**：内存扰动库值 → **界面断言必须变红**（证明断言承重）
- 结果写回台账能对上的地方，备注带 `[界面·无头]` / `[界面·窗口]`
- 页面上「已覆盖界面断言的用例」数字**真的上升**（从 1 → ≥7）
