## 一、这个活的唯一红线

**绝不产出假的"通过"。**

背景：上一版工具把 237 条**从未执行过**的用例改写成"通过"，团队拿到的验收结论是假的。
所以这里每写一条"通过"，都是在向用户交付一个结论。**宁可少交几条经得起复现的，
也不要交一批"看着全通过"的。**

具体到操作，就是三条铁律：

### 铁律 1：断言必须**能失败**

写完一条断言，先问自己：**"如果系统真的错了，这条断言会不会红？"**
如果不会（比如"接口返回 200 就算过""字段存在就算过""有数据就算过"），那它不是断言，是装饰。

- ✅ 等式断言：`报表金额 == 库中 SUM(TOT_COST)`、`重算 qty == 单次量×频次×天数`
- ❌ 存在性断言：`data 不为空 → 通过`

### 铁律 2：**口径没吃透之前，任何"差异"都先当自己的错**

这个系统里绝大多数"看起来是缺陷"的现象，最后都是口径问题（见第四节）。
**在能用一个等式复现出来之前，不要写进缺陷清单，也不要判失败。**

### 铁律 3：写入类必须**净零**

造的数据要么能删、要么能反向冲平（退费/退号/删除）。
收尾失败要在结论里如实说"本次残留了什么"，不能装作没发生。

> 本环境**没有测试库回滚**，且用户**要求保留测试数据**，所以：
> 残留"测试患者"这种是可以的（用户明确接受），
> 但残留"多收的钱""假的可退挂号"这种**会误导真人**的不行。

## 二、标准作业流程（每条用例）

### 第 0 步：先读用例的「预期」，把它翻译成一个**等式**

用例表给的是"载入准确且勾选规则生效"这种话，**它不是断言**。你要把它翻译成：

> "接口返回的待缴明细 N 条 与库中 `balance_flag=0` 的条数相等，
>  且逐条 applyId 的 数量/单价/金额 完全一致"

**翻译不出来，说明口径还没吃透——停下来去查库、查接口，别急着写代码。**

### 第 1 步：找权威数据源

- **接口全貌**：`data/api_spec.json`（Swagger，1590 条路径）。先按 `summary` 关键词搜。
- **前端怎么调的**：页面 chunk 里的真实请求最权威。前端是 Vite 打包，
  入口 `http://192.168.1.198:8088/index.html` → `static/js/index-*.js`（含路由表 router chunk）
  → 路由里的 `import("./xxx-<hash>.js")` 就是对应该页面的 chunk。
  拉下来 grep `url:` 或接口路径即可。**我摸清的口径基本都是这么来的。**
- **数据库**：`xchis/xchis@192.168.1.199:1521/orcl`。先 `user_tab_columns` 看列名，
  再按业务关键词猜表名（`FIN_OP_*` 门诊费用 / `FIN_IP_*` 住院 / `PHA_*` 药房 / `MED_OP_*` 门诊医嘱 / `BD_*` 基础字典）。

### 第 2 步：只读优先

能用**已存在的数据**验证，就不要造数。造数是有成本的（可能残留、可能撞车）。

### 第 3 步：写 flow（在 `verify/flows/<模块>.py`，见第五节）

标准骨架：

    created = []                      # 写入类：记下造了什么，finally 里收尾

        # ③ 回读（接口 + Oracle 双向）
        # ④ 断言 —— 每一条都要能失败，失败要给出"接口 X vs 库 Y"的具体数字
        bad = []

**判定语义（严格遵守）**：

| 状态 | 什么时候用 |
|---|---|
| **通过** | 所有断言都成立，且证据可复现 |
| **失败** | 断言不成立（真差异），或执行异常 |
| **未执行** | **压根没有可验证的数据/条件**（不是"验了没过"）。备注要写清"缺什么、为什么" |

⚠️ **最容易犯的错**：把"没数据可验"写成"失败"，或者反过来把"验证不了"凑成"通过"。

### 第 4 步：跑 — 但别只跑一次

```bash
python run_verify.py --closed-loop --cases LX-YYY     # 单跑
python run_verify.py --closed-loop                    # 全量（看有没有互相干扰）
```

**写完至少连跑 3 次全量**。这个项目里我踩过两个"偶发假失败"：
- **造数撞车**：身份证号只有 1000 个组合，固定种子必然重复 → 建档失败
- **共享资源竞争**：挂号号序是共享池，别人插队会让"连号"断言假失败

**凡是靠"别人不动作"才成立的断言，都是不稳的**，要改成不依赖外部时序的判据
（例：号序连续性改成判"号源池在 [min,max] 内无空洞"，而不是判"我这 5 个连号"）。

### 第 5 步：写回追踪表

```bash

```

## 三、写"未执行"也是一份交付

不要因为"没验成"就觉得白干。**一条说得清楚的"未执行"比一条含糊的"通过"值钱得多。**

好的"未执行"备注长这样：

> 库中当前没有「已挂单但未执行」的住院退药单（退药单执行即消耗）。参考：退药单 DIS1740 已于
> 2026-10-09 15:40:58 实测执行过一次 —— 配药确认+发药确认均成功、2/2 条明细流转到已发药、
> 库存按退药量回补、出入库流水 BEFORE/AFTER 自洽、并与原医嘱镜像对应。

它同时告诉了用户三件事：**为什么现在验不了**、**本来能验什么**、**已知的结论是什么**。

反过来，"未执行：需真实业务前置"这种通用话术，只有在确实说不清时才能用。

## 四、假缺陷速查（碰到这些先怀疑自己）

> 完整版在交接文档第 5 节。这里只放最高频的。**

1. **前端 hash 跳转不加载组件** → 点完菜单内容区还是仪表盘。不是页面坏了，要整页 reload。
2. **`dayBalanceId` 口径**：门诊/挂号日结报表只传时间区间 → **永远返回 0**。
   必须传 `dayBalanceId`，且只认**当前登录操作人**的日结。
3. **别把"分项"当"总额"**：日结报表的 `feeInfoList` 是费用分项，
   页面上看到的"检查费 427.70"可能只是其中一行（真总额 1802.43）。
4. **挂号日结的退费票据金额是挂号费不是实收**（`regCost` vs `totalCost`，差在优惠）。
5. **`FIN_OP_APPLY` 待缴口径** = `balance_flag='0' AND valid_flag='1'`；
   `needCharge/list` 返回的是**按处方号分组**的，`len(data)` 是组数不是条数。
6. **`register/view/list` 的 `total` 不是可退条数**，只能看 `data` 行数。
7. **病历/字典会漂移**：挂号级别→诊查费字典被改过，历史单据对不上当期字典是正常的。
8. **接口会过滤停用项**：查出来的比库里少，先确认自己有没有带上 `VALID_FLAG='1'` 这类条件。
9. **写入后某些字段不回写**：退药执行后明细 `OUTPUT_TIME` 仍为空（只有单头写），
   别拿它当"已发药"判据。
10. **管理员令牌查不到某些数据**：退费确认按科室隔离、日结按操作人隔离——先怀疑身份，别急着报缺陷。

## 五、怎么多人/多 AI 并行

### 5.1 放哪：`verify/flows/<模块>.py`（不要改公共文件）

```python
# verify/flows/l5_emr.py
from ..closed_loop import Ctx, LoopResult, _oracle_conn

def flow_L5_001(ctx): ...
FLOWS = {"L5-001": flow_L5_001}
```

`closed_loop.py` 末尾会自动 `collect()` 并进去（`verify/flows/__init__.py`）。
**各自一个文件 → 不会冲突。** 某个文件写坏了只会打印一行"跳过"，
不会拖垮别人的用例（已做异常隔离）。

### 5.2 建议的分工（按模块切，天然不重叠）

| 模块 | 用例段 | 说明 |
|---|---|---|
| 门诊挂号/收费/退费 | L6-0xx | **已完成大半**，剩下 L6-027/032/043 |
| 医生站/医嘱 | L2-1xx、L4-048 | 门诊医嘱机器已就绪（见交接文档 5.11） |
| 住院药房 | L9-0xx | 摆药机器已就绪（5.12）；剩 L9-012/013 |
| **EMR 病历文书** | L5-0xx（约 24 条，最大一块） | **需要先摸链路**：在院患者、模板、签名 |
| 统计/一致性 | L5-033/034/035/036 | 注意 033/034 本环境**无接口** |
| 打印/医保/电子发票/CA | — | 物理做不了，用户说先跳过 |

**认领方式**：开工前在下面这张表里占位（或口头说清"我做 L5-0xx"），做完把状态改掉。

> 当前已认领/已完成（26 条）：L2-105、L2-107、L6-001/002/004/005/008/009/012/014/015/018/020/
> 024/025/028/033/036/039/045/046/047/050/052、L9-010/011（+L9-014 带证据的未执行）

### 5.3 公共资源要错开

- **不要随便新建挂号**：收过费就永久退不了号（见交接文档 5.8），
  收费类用例请复用"试验台就诊"
- **不要动别人的证据**：`reports/verify/closed_loop_latest.json` 是全量跑覆盖的，
  想留证据就存成 `closed_loop_<时间>.json`
- **`verify/closed_loop.py` 是公共文件**：除非改公共机制（比如加 helper），否则别动。
  要加 helper，先跟其他人说一声

### 5.4 提交前自检（照着打勾）

- [ ] 断言是**等式**，不是"存在即通过"
- [ ] 断言**能失败**（能说出"系统错成什么样它会红"）
- [ ] 失败信息里带了**具体数字**（"接口 X vs 库 Y"），不是一句"不一致"
- [ ] `evidence` 里有能让人**复现**的键值（ID、金额、条数、SQL 依据）
- [ ] 写入类**净零**（收尾在 `finally` 里，且验证了收尾结果）
- [ ] 连跑 3 次全量都稳
- [ ] 状态用词只用：通过 / 失败 / 未执行
- [ ] 备注是**客观情况**，没写"自动化测试""脚本验证"之类标签
- [ ] 跑了 `update_tracking_excel.py` 且**没覆盖源文件**

## 七、最后

用户要的不是"跑完 87 条"，是**一份能拿去验收的真结论**。

- 验不动就老实说验不动，把原因和已知结论写清楚
- 验出真失败**只记录，不要动缺陷追踪表**
- 有判断不了的口径，**直接问用户**——他愿意答（本轮 L9-014 就是这么定的）

**别为了凑数把没验的写成通过。那正是这个项目要修的病。**
